- purpose: private-network access through two session modes: **Browse the web** uses an in-app browser with a loopback SOCKS5 proxy; **Forward ports** exposes server-direct TCP forwards to other apps at localhost, without a browser or SOCKS5 listener. Fresh sessions start with forwards off; their controls are in forwarding mode. The browser split-tunnels by the server's domain/CIDR rules; forwards always use the server and reject off-list targets. This is an access browser, not a privacy/anonymity browser
- connection settings live in named profiles (`ProfileStore`) as on the desktop — server node id, auth-key reference, relay URLs, relay token and port forwards are per profile — but only the selected profile connects, one session at a time. Auth keys are one shared list (`AuthKeyStore`, Keychain) that profiles reference by id
- strict no backward compatibility
- make change on sibling project ../flextunnel, which is the library used by this project, if needed 
- the Rust artifact (libflextunnel.xcframework) is delivered via a local Swift package `Packages/Flextunnel/Package.swift` (referenced by local path in project.yml); its binary target downloads the pinned release zip by URL+checksum (reproducible; SPM auto-exposes the embedded flextunnel.h to the bridging header, so no vendor/ dir and no HEADER_SEARCH_PATHS). Bump to a new release with `scripts/bump-xcframework.sh <tag>` (rewrites url+checksum). For FFI dev against a local Rust build, run `./build-ios.sh` in the sibling then set `FLEXTUNNEL_LOCAL_XCFRAMEWORK=1` for both `xcodegen generate` and `xcodebuild` — SPM forbids binary paths outside the package root, so the sibling's dist/ios is reached via the committed symlink `Packages/Flextunnel/local/libflextunnel.xcframework`
- local CI runs on macOS, including the development VM: `ci/ci.sh` defaults to Simulator build, launch smoke test, unit tests and unsigned-archive checks. Signed device builds (`device`) and sibling-working-tree integration (`ffi`) are opt-in. The phone is paired with `machost`; the VM can never pair with it (`docs/deploy-from-a-vm.md`); `scripts/run-device-ios-host.sh` builds its own signed Release app here and installs/launches it there over SSH. Use its `status` command to check the phone. See `docs/local-ci.md`
- unit tests: `Sources/FlextunnelTests` (`ci/ci.sh unit`, in the default set) cover the app's pure logic; keep `RouteMatchTests` in step with flextunnel-core's `routed_set.rs` tests when the routing rules change there
- browser e2e UI tests: `ci/e2e.sh` runs `Sources/FlextunnelUITests` on a simulator here, against a real flextunnel server it builds at the pinned tag and starts on loopback (fixture site behind host alias `e2e.flextunnel.test`). Add or update a test when changing browser UX, and give new controls an `accessibilityIdentifier`. See `docs/local-ci.md`
- target iOS 26 unless the webkit is downgraded to WKWebView
- regenerate the project from project.yml after code changes (`xcodegen generate`)
- the iOS client is **alpha** (iOS suspends the in-process tunnel in the background and there is no Network Extension, so it is less stable than the other flextunnel clients): every release is a GitHub prerelease titled `Alpha`, the README carries an alpha notice and the in-app version footer says `alpha` (`AppVersion.stage`); change all three together when it graduates
- releases are tagged `v<MARKETING_VERSION>` (from project.yml) by `.github/workflows/unsigned-ios.yml`, which refuses an existing tag: bump `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` on both the app and widget targets, keeping them equal, before triggering a release
- build/verify against the simulator with arm64 forced, no device/OS pinned: `xcodebuild -project Flextunnel.xcodeproj -scheme FlextunnelApp -destination 'generic/platform=iOS Simulator' ARCHS=arm64 build` — the libflextunnel.xcframework is arm64-only, so a generic destination without `ARCHS=arm64` picks x86_64 and fails to link (`arch=` is not a valid destination key; only `ARCHS` works). To run on a booted simulator instead, name it: `-destination 'platform=iOS Simulator,name=iPhone 17'` (leave `OS=` off so it tracks whatever runtime is installed)
- always use uv to run python scripts
